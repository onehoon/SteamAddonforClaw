4. HHC — MSI CLAW DIRECTINPUT CONTROLLER
===============================================================================

HHC recognizes the MSI Claw DirectInput controller using MSI vendor/product
IDs.

MSI Vendor ID:
  VID 0x0DB0

Relevant Product IDs:
  PID 0x1901 = XInput
  PID 0x1902 = DirectInput
  PID 0x1903 = testing/other mode

ControllerManager creates DClawController for:

  VID 0x0DB0
  PID 0x1902
  PID 0x1903

The normal DirectInput routing target is PID 0x1902.


===============================================================================
5. HHC — DIRECTINPUT DEVICE MATCHING
===============================================================================

DClawController inherits from DInputController.

DInputController.AttachDetails() does not select a controller only from
VID/PID.

It enumerates DirectInput gamepad devices and creates a Joystick for each
candidate.

For each joystick it obtains:

  joystick.Properties.InterfacePath

It then converts the HID symbolic/interface path into a PnP identity and
compares it with the selected PnPDetails.SymLink.

Conceptually:

  DirectInput DeviceInstance
      ->
  Joystick
      ->
  InterfacePath
      ->
  HID/PnP symbolic identity
      ->
  compare with selected physical PnPDetails

Therefore HHC's production behavior supports the same basic principle used
by SteamInputAddonforClaw:

  Do not acquire "the first VID/PID match".

Instead:

  Select an exact verified DirectInput interface belonging to the intended
  physical controller.


===============================================================================
6. HHC — MSI CLAW BUTTON MAPPING
===============================================================================

DClawController.Tick() directly reads SharpDX DirectInput JoystickState.

Confirmed rear-button indices:

  M1 = state.Buttons[15]
  M2 = state.Buttons[16]

HHC maps them internally as:

  M1 -> ButtonFlags.OEM3
  M2 -> ButtonFlags.OEM4

This independently confirms that M1 and M2 are separately visible in
DirectInput.

SteamInputAddonforClaw must continue to obtain M1/M2 from DirectInput.

Do not derive M1/M2 from XInput.


===============================================================================
7. HHC — OTHER DIRECTINPUT AXIS/BUTTON CHARACTERISTICS
===============================================================================

The reviewed DClawController implementation contains the following mapping.

Face buttons:

  Buttons[1]  -> A
  Buttons[2]  -> B
  Buttons[0]  -> X
  Buttons[3]  -> Y

Shoulders:

  Buttons[4]  -> L1
  Buttons[5]  -> R1

Digital full-trigger buttons:

  Buttons[6]  -> L2 Full
  Buttons[7]  -> R2 Full

Menu buttons:

  Buttons[8]  -> Back
  Buttons[9]  -> Start

Stick clicks:

  Buttons[10] -> Left Stick Click
  Buttons[11] -> Right Stick Click

Rear buttons:

  Buttons[15] -> M1
  Buttons[16] -> M2


D-pad uses POV values.

Left stick:

  X -> Left Stick X
  Y -> Left Stick Y, inverted

Right stick:

  Z         -> Right Stick X
  RotationZ -> Right Stick Y, inverted

Analog triggers:

  RotationX -> L2
  RotationY -> R2

HHC maps raw unsigned DirectInput ranges into its normalized state.

These characteristics should be re-verified again before implementing the
final Classic Steam Controller report mapper.

They should not be silently assumed only from this document if the HHC
reference revision changes.


===============================================================================
8. HHC — PNPDETAILS IDENTITY MODEL
===============================================================================

PnPDetails stores at least two distinct controller identities:

  deviceInstanceId

  baseContainerDeviceInstanceId


It also stores:

  devicePath
  baseContainerDevicePath
  SymLink
  EnumeratorName
  InterfaceGuid
  VID/PID
  virtual/physical flags
  internal/external flags


Meaning observed from DeviceManager:

deviceInstanceId:
  The actual selected HID PnP device instance.

baseContainerDeviceInstanceId:
  A higher/base physical PnP identity selected while walking the device
  topology.

This distinction is important for HidHide.


===============================================================================
9. HHC — HOW BASE CONTAINER IDENTITY IS DERIVED
===============================================================================

DeviceManager.GetDetails() begins from the HID interface/device.

It walks upward through the PnP topology.

The traversal attempts to find a useful base device associated with the same
controller rather than treating only the leaf HID collection as the complete
physical controller identity.

PnPDetails is finally populated with both:

  deviceInstanceId
  baseContainerDeviceInstanceId

Therefore HHC intentionally retains both:

  selected HID child identity
  physical/base controller identity


===============================================================================
10. HHC — HIDHIDE TARGET SELECTION
===============================================================================

This was the most important finding for PR #77.

IController.HideHID() currently performs:

  HidHide.HidePath(Details.baseContainerDeviceInstanceId)
  HidHide.HidePath(Details.deviceInstanceId)

UnhideHID() performs the inverse:

  HidHide.UnhidePath(Details.baseContainerDeviceInstanceId)
  HidHide.UnhidePath(Details.deviceInstanceId)

Therefore HHC does NOT hide only one selected HID child.

The current production pattern is:

  physical/base controller PnP identity
      +
  selected controller/HID PnP identity
      ->
  HidHide BlockedInstanceIds


This applies generically through IController and is used by MSI Claw
DClawController as part of HHC's controller lifecycle.


===============================================================================
11. HHC — PREVIOUS FULL-TREE HIDING APPROACH
===============================================================================

IController.cs also contains older/commented logic that would enumerate a
base device and its children and hide every discovered instance.

That code is currently commented out.

The active implementation instead uses only:

  baseContainerDeviceInstanceId
  deviceInstanceId

This is important.

HHC appears to have narrowed hiding from an entire tree to two specific
identities.

For SteamInputAddonforClaw this supports the design rule:

  Hide the minimum exact topology needed.

Do not recursively hide every child of the MSI controller unless future
hardware evidence proves it necessary.


===============================================================================
12. HHC — ISHIDDEN SEMANTICS
===============================================================================

IController.IsHidden() checks:

  HidHide.IsRegistered(Details.baseContainerDeviceInstanceId)

Therefore HHC treats the base-container registration as a primary indicator
that the physical controller is hidden.

This is another indication that base identity is significant and should not
be discarded when designing MSI Claw isolation.


===============================================================================
13. HHC — HIDHIDE IMPLEMENTATION
===============================================================================

HHC's HidHide wrapper uses Nefarius HidHideControlService.

Relevant concepts:

  service.ApplicationPaths
  service.BlockedInstanceIds
  service.IsActive

HidePath():

  If the exact deviceInstancePath is not already in BlockedInstanceIds,
  add it.

UnhidePath():

  If the exact deviceInstancePath exists in BlockedInstanceIds,
  remove it.

The semantics are exact instance IDs, not VID/PID-wide rules.


===============================================================================
14. HHC — HIDHIDE FALLBACK
===============================================================================

If the HidHideControlService API cannot be used, HHC has a fallback to
HidHideCLI.

Relevant CLI concepts:

  --app-reg
  --app-unreg
  --dev-hide
  --dev-unhide
  --cloak-on
  --cloak-off

SteamInputAddonforClaw currently uses its own direct driver/API integration,
so there is no reason to copy this HHC fallback architecture.

The useful reference fact is the identifier semantics:

  HidHide device entries are PnP device instance paths/IDs.


===============================================================================
15. HHC — APPLICATION WHITELIST LIFECYCLE
===============================================================================

HHC registers its own executable with HidHide during application startup.

Conceptually:

  register HHC executable
      ->
  later hide physical controllers

Therefore the application has permission to keep accessing hidden devices.

This supports SteamInputAddonforClaw's planned mutation ordering:

  whitelist addon executable first
      ->
  hide physical controller second


===============================================================================
16. HHC — GLOBAL CLOAKING STATE
===============================================================================

HHC also enables HidHide globally when its ControllerManager starts:

  HidHide.SetCloaking(true)

This behavior should NOT be copied into SteamInputAddonforClaw.

Reason:

SteamInputAddonforClaw has a stricter ownership rule:

  Existing HidHide configuration is not owned by the addon.

Therefore our addon should not globally enable/disable HidHide as part of
normal routing.

Current project rule remains:

  New PhysicalIsolation may start only when HidHide is already in a supported
  Available/active state.

Recovery may still remove addon-owned entries when the HidHide configuration
is readable even if active state later changed.


===============================================================================
17. HHC — HIDE() AND POWER CYCLING
===============================================================================

IController.Hide() performs:

  HideHID()

and optionally:

  CyclePort()

Unhide() similarly calls UnhideHID() and optionally CyclePort().

ControllerManager intentionally calls Hide outside certain controller locks
because port cycling can block for several seconds and trigger device/UI
state transitions.

This is useful as evidence that hiding a physical controller can interact
with PnP lifecycle and device arrival/removal.

SteamInputAddonforClaw #77 currently should NOT introduce port cycling merely
because HHC does so.

Whether the MSI Claw requires an explicit cycle for our DirectInput routing
must be determined by hardware testing.

Do not assume HHC's entire controller-manager lifecycle is necessary for the
addon.

21. DS4WINDOWS — HIDHIDE HANDLE ACCESS
===============================================================================

HidHideAPIDevice opens the HidHide control device with:

  GENERIC_READ

and, when writes are required:

  GENERIC_READ | GENERIC_WRITE

This confirms the write access contract adopted in PR #76.


===============================================================================
22. DS4WINDOWS — BLACKLIST STORAGE
===============================================================================

Persistent HidHide blacklist operations use the complete blacklist as a
MULTI_SZ.

SetBlacklist():

  read/create complete list
      ->
  serialize full MULTI_SZ
      ->
  SET_BLACKLIST

Therefore a high-level "add one entry" API still must preserve all unrelated
entries.

SteamInputAddonforClaw's #76 behavior:

  Inspect complete configuration
      ->
  add/remove one exact entry
      ->
  write complete list

matches this requirement.


===============================================================================
23. DS4WINDOWS — ACTUAL PHYSICAL CONTROLLER HIDHIDE IDENTITY
===============================================================================

ControlService does not hide a physical controller using only VID/PID.

For a DS4Device it uses:

  dev.HidDevice.DevicePath

and converts that device path through:

  Global.GetInstanceIdFromDevicePath(...)

The resulting exact PnP instance ID is the identifier passed to HidHide.

Conceptually:

  physical HID symbolic path
      ->
  exact PnP device instance ID
      ->
  HidHide blacklist/session blacklist


This reinforces:

  Never hide all devices matching VID/PID.


===============================================================================
24. HHC VS DS4WINDOWS TARGET DIFFERENCE
===============================================================================

HHC:

  baseContainerDeviceInstanceId
  +
  deviceInstanceId

DS4Windows:

  selected HID device's exact PnP instance ID


This difference should not automatically be treated as a contradiction.

DS4Windows primarily manages ordinary physical Sony-compatible HID devices.

HHC is managing handheld/composite-controller topology and explicitly keeps
both a selected HID device identity and a base physical controller identity.


Project decision:

For MSI Claw-specific routing, prefer HHC behavior unless live hardware
testing proves a different minimal set is sufficient.

25. DS4WINDOWS — MANAGED HIDHIDE SETS
===============================================================================

The reviewed fork tracks separate case-insensitive sets for HidHide ownership.

Examples:

  hidHideSessionManagedInstanceIds
  hidHidePersistentManagedInstanceIds

String comparison is OrdinalIgnoreCase.

This supports exact, case-insensitive PnP identity handling.


===============================================================================
26. DS4WINDOWS — EXISTING PERSISTENT ENTRY ADOPTION
===============================================================================

Important behavioral difference.

DS4Windows checks whether a target instance ID already exists in the
persistent blacklist.

If it exists, the reviewed fork can "adopt" that entry into its managed
persistent set.

Later managed cleanup may release/remove managed persistent entries.

This should NOT be copied into SteamInputAddonforClaw.


SteamInputAddonforClaw ownership rule is stricter:

  pre-existing entry
  != addon-owned entry

If an entry existed before the addon session:

  do not journal it as an addition
  do not claim ownership
  do not remove it during rollback


This protects:
  - user HidHide configuration
  - ClawTweaks configuration
  - HHC configuration
  - other controller tools


===============================================================================
27. DS4WINDOWS — SESSION BLACKLIST API
===============================================================================

The reviewed DS4Windows fork contains additional IOCTLs:

  IOCTL_ADD_SESSION_BLACKLIST = 0x80016020
  IOCTL_CLR_SESSION_BLACKLIST = 0x80016024

The source comments describe these as process-lifetime HidHide entries that
are automatically removed when the process exits.

However, the same source explicitly notes that released HidHide 1.5 builds
do not expose this API and therefore callers require a fallback.

SteamInputAddonforClaw v1 baseline:

  HidHide 1.5.230

Therefore SteamInputAddonforClaw must NOT depend on session-blacklist IOCTLs.

Current design remains:

  persistent exact HidHide additions
  +
  RecoveryManager journal
  +
  exact normal rollback
  +
  startup crash recovery


===============================================================================
28. DS4WINDOWS — SESSION CLEANUP
===============================================================================

DS4Windows cleanup distinguishes session-managed and persistent-managed
entries.

Persistent cleanup:

  GetBlacklist()
      ->
  remove only managed exact IDs
      ->
  SetBlacklist(updated list)

This confirms the generic principle that unrelated entries must remain
untouched.


===============================================================================
29. DS4WINDOWS — VIRTUAL OUTPUT HIDHIDE INTERACTION
===============================================================================

The reviewed ControlService also contains logic specifically protecting
virtual VIIPER outputs from accidental HidHide containment.

It distinguishes physical input hiding from virtual output devices.

It contains logic described as preventing newly created VIIPER virtual Sony
outputs from remaining accidentally blacklisted.

This will be particularly important for the future SteamOutput PR.

Project implication for later work:

  addon-owned VIIPER outputs must never be mistaken for external physical
  controllers or physical HidHide targets.

Track addon-created virtual devices explicitly.

31. TARGET REPO — DIRECTINPUT TOPOLOGY
===============================================================================

DirectInputDeviceTopologyResolver begins with the DirectInput interface path.

It extracts the exact PnP instance ID from the path.

It then enumerates present PnP devices and requires exactly one matching
device.

The PnP interface must satisfy:

  Vendor ID  = 0x0DB0
  Product ID = 0x1902

and gamepad usage:

  UsagePage = 0x0001
  Usage     = 0x0005

It then walks ancestor instance IDs looking for:

  USB\VID_0DB0&PID_1902\...

The result stores:

  PnpInstanceId
  PhysicalIdentity


Therefore current project topology already provides two useful identities.

33. PROJECT DECISION — PHYSICALISOLATION TARGET SET
===============================================================================

Based on HHC production behavior, the preferred #77 target set is:

  PhysicalIdentity
  PnpInstanceId

Case-insensitive exact duplicate entries should be collapsed.

Do not perform another broad PnP scan inside PhysicalIsolation.

The source of both IDs must remain the already verified/owned PhysicalInput

===============================================================================
34. PROJECT DECISION — FORWARD MUTATION ORDER
===============================================================================

Preferred mutation order:

  1. addon executable whitelist
  2. PhysicalIdentity HidHide entry
  3. PnpInstanceId HidHide entry


Reason:

  - application access is established before hiding
  - base/physical identity is registered
  - selected HID child is then registered
  - order is deterministic and journalable


===============================================================================
35. PROJECT DECISION — ROLLBACK ORDER
===============================================================================

Rollback should be the strict reverse:

  1. PnpInstanceId
  2. PhysicalIdentity
  3. addon executable whitelist


Each addon-owned entry must be restored independently.

Recovery journal completion should occur immediately after each exact restore
is verified.


===============================================================================
36. PROJECT DECISION — PRE-EXISTING ENTRIES
===============================================================================

For every target independently:

If present before PhysicalIsolation:

  owner = external/pre-existing

Do not:

  RecordHidHideDeviceAddition
  AddHiddenDevice
  remove during rollback


Example:

Before session:

  PhysicalIdentity already hidden
  PnpInstanceId not hidden

Then addon owns only:

  PnpInstanceId addition

Rollback removes only:

  PnpInstanceId

PhysicalIdentity remains untouched.


===============================================================================
37. PROJECT DECISION — AMBIGUOUS MUTATION
===============================================================================

This is stricter than HHC/DS4Windows and is required by the project recovery
model.

Before each actual mutation:

  RecoveryManager record must succeed.

If API call fails/throws, inspect actual configuration.

Case A:
  exact entry verified present

Meaning:
  mutation happened despite API failure.

Action:
  preserve journal evidence
  treat mutation as needing rollback
  fail Execute
  generic pipeline rollback should restore it


Case B:
  exact entry verified absent

Meaning:
  mutation did not happen.

Action:
  complete/remove that recovery record
  fail Execute


Case C:
  configuration cannot be inspected

Meaning:
  actual mutation state is unknown.

Action:
  preserve journal evidence
  fail closed

Critically:

  Do NOT remove the addon whitelist while a physical HidHide mutation may
  still exist but cannot be verified/restored.


===============================================================================
38. PROJECT DECISION — PARTIAL TWO-DEVICE FAILURE
===============================================================================

Example:

  whitelist added successfully
  PhysicalIdentity added successfully
  PnpInstanceId add fails

Rollback must be able to restore:

  PnpInstanceId if possibly/actually added
  PhysicalIdentity
  whitelist

If PnpInstanceId state is ambiguous:

  do not proceed to PhysicalIdentity/whitelist cleanup in a way that could
  reduce recovery access or discard evidence.

Leave recovery state fail-closed.


===============================================================================
39. PROJECT DECISION — HIDHIDE ACTIVE STATE
===============================================================================

HHC and DS4Windows have broader ownership models and may manipulate HidHide
active state.

SteamInputAddonforClaw does not.

New PhysicalIsolation:

  HidHide Available
  -> may proceed

HidHide Disabled:
  -> do not start a new isolation session

InverseWhitelist:
  -> do not start a new isolation session

NotInstalled / AccessDenied / ConfigurationUnavailable:
  -> fail closed


Recovery differs:

If configuration remains readable, addon-owned entries may still be removed
during recovery even if HidHide is Disabled or InverseWhitelist.

This was established in PR #76.


===============================================================================
40. PROJECT DECISION — NO POWER CYCLE YET
===============================================================================

HHC may power-cycle controllers after hide/unhide.

SteamInputAddonforClaw should not add this only because HHC does.

Current approach:

  - exact HidHide mutation
  - maintain acquired DirectInput source
  - verify behavior on hardware

If hardware testing proves that physical hiding is not effective until
re-enumeration/power cycling, investigate that as a separate hardware-specific
change.

Do not introduce it speculatively.


===============================================================================
41. PROJECT DECISION — DEFAULT PRODUCTION PLAN
===============================================================================

PR #77 must NOT hide the controller in ordinary production routing yet.

Until SteamOutput exists:

  NativeMode             Enabled
  PhysicalInput          Disabled
  PhysicalIsolation      Disabled
  ThirdPartyIsolation    Disabled
  SteamOutput            Disabled
  XboxOutput             Disabled
  GameBarRouting         Disabled


Reason:

Enabling:

  PhysicalInput
  PhysicalIsolation

before replacement SteamOutput exists would produce:

  physical controller hidden
  +
  no virtual replacement controller

which would break normal game input.

  M2 -> Classic Steam Controller Left Grip
  M1 -> Classic Steam Controller Right Grip


Do not change this mapping based only on HHC OEM3/OEM4 naming.

45. SOURCE-DERIVED FACT VS PROJECT INFERENCE
===============================================================================

The following are directly verified source behaviors:

HHC:
  - DClawController uses PID_1902/1903.
  - M1 = Buttons[15].
  - M2 = Buttons[16].
  - HideHID registers both baseContainerDeviceInstanceId and deviceInstanceId.
  - UnhideHID removes both.
  - IsHidden checks baseContainerDeviceInstanceId.
  - HidHide operates on exact BlockedInstanceIds.
  - HHC registers its application and manages global cloaking.

DS4Windows:
  - physical HID DevicePath is converted into exact PnP instance ID.
  - persistent blacklist is MULTI_SZ.
  - SET_BLACKLIST is 0x8001600C.
  - writes use GENERIC_READ | GENERIC_WRITE.
  - managed IDs are case-insensitive.
  - session blacklist IOCTL support exists in this fork but released HidHide
    1.5 compatibility requires persistent fallback.
  - virtual VIIPER outputs require explicit protection from accidental HidHide
    containment.


The following are SteamInputAddonforClaw project decisions/inferences:

  - HHC baseContainerDeviceInstanceId is best represented by our
    PhysicalIdentity.

  - HHC deviceInstanceId is best represented by our PnpInstanceId.

  - MSI Claw PhysicalIsolation should therefore start with a two-entry target
    model.

  - Addon ownership must be stricter than HHC/DS4Windows and must never adopt
    pre-existing entries.

  - Normal rollback must be strict reverse mutation order.

  - Global HidHide state must remain untouched.

  - No controller power cycle should be added until hardware testing proves it
    necessary.

===============================================================================
1. PHYSICAL CONTROLLER CONTRACT
===============================================================================

The Addon's Stock MSI Center M routing path acquires the built-in MSI controller in PID_1902 DirectInput mode.

Verified physical contract retained from the original research:

  USB VID/PID: 0DB0:1902
  primary gamepad collection used by the Addon:
    HID\VID_0DB0&PID_1902&MI_00&COL01\...

The physical root and sibling collections remain topology/identity evidence and are not blanket HidHide targets.

The Addon must resolve the DirectInput descriptor to the expected MSI gamepad PnP identity before acquisition. VID/PID count alone is not enough.

===============================================================================
2. VERIFIED CONTROL SEMANTICS
===============================================================================

The original physical research established these MSI Claw semantics used by the current normalized ControllerState pipeline:

  A/B/X/Y and ordinary gamepad buttons
  8-way D-pad
  LB / RB
  analog LT / RT travel
  independent LT / RT digital full-pull buttons
  left analog stick
  right analog stick
  L3 / R3
  M1 / M2 rear buttons

Important independent trigger contract:

  Buttons[6] -> LeftTriggerFull
  Buttons[7] -> RightTriggerFull

These digital full-pull states are independent from analog trigger travel and must remain independent after normalization.

Rear-button contract used by the Addon:

  M1 -> Buttons[15]
  M2 -> Buttons[16]

Physical position, viewed from the front:

  M1 = right rear
  M2 = left rear

The normalized physical state should preserve that side identity. The output mapper decides whether those buttons become Gordon grips, Steam Deck R4/L4, or another future target.

===============================================================================
3. AXIS / REPORT REFERENCE
===============================================================================

The retained DirectInput research maps the physical 16-bit axis slots from the PID_1902 input report as follows:

  X      @ report offset 0x0D
  Y      @ report offset 0x0F
  Z      @ report offset 0x11
  RotX   @ report offset 0x13
  RotY   @ report offset 0x15
  RotZ   @ report offset 0x17

The DirectInput interpretation used by the Addon normalizes the stick and trigger sources rather than forwarding raw report offsets to the virtual output.

Trigger analog values are normalized independently from the digital full-pull button state.

Do not make the physical parser depend on Steam Deck trigger units, Gordon trigger units, or any later virtual-controller report scale.

===============================================================================
4. D-PAD
===============================================================================

The physical D-pad is normalized before virtual-output mapping.

Recent real-hardware diagnostics established that physical D-pad transitions and canonical mapped transitions could match state-for-state with low millisecond latency. Therefore a future output target must consume the normalized D-pad rather than re-reading physical HID state or inventing a target-specific physical parser.

Steam Deck mapping should be direct:

  physical normalized Down  -> SteamDeck DPadDown
  physical normalized Left  -> SteamDeck DPadLeft
  physical normalized Right -> SteamDeck DPadRight
  physical normalized Up    -> SteamDeck DPadUp

===============================================================================
5. RIGHT STICK / R3
===============================================================================

The physical layer exposes a real right stick and R3.

Historical Gordon output policy translated them to:

  right stick -> Gordon right pad
  R3          -> Gordon right-pad press

That translation is output-specific and must not exist in the normalized physical state.

Steam Deck provides native:

  RStickX
  RStickY
  R3

so the new mapper should use those directly.

===============================================================================
6. REAR BUTTON OUTPUT POLICY
===============================================================================

Historical Gordon mapping:

  M1 / right rear -> Right Grip
  M2 / left rear  -> Left Grip

Initial Steam Deck mapping target:

  M1 / right rear -> R4
  M2 / left rear  -> L4

L5/R5 remain neutral on MSI Claw until a supported device actually supplies additional rear controls.

Future handheld support should evolve the normalized auxiliary-control model so four rear buttons can be represented without changing the Steam Deck ABI.

===============================================================================
7. OEM1 / QUICK ACCESS
===============================================================================

OEM1 is not part of the current normalized ControllerState contract documented by the original PID_1902 research.

The Steam Deck target provides a native `QuickAccess` field, so OEM1 is a promising future physical source for QAM behavior.

However, OEM1 must be researched as its own physical input/capability path before mapping. Do not assume it is another PID_1902 gamepad button and do not steal WING or another unrelated native control.

See SD5 in `VIIPER_MIGRATION_TODO.md`.

===============================================================================
8. HIDHIDE OWNERSHIP CONTRACT
===============================================================================

The Addon may hide only the exact PID_1902 primary gamepad collection it has safely acquired and identified for the current routing session.

Preserve these rules:

  - do not hide the MSI physical root;
  - do not hide PID_1901;
  - do not hide unrelated PID_1902 sibling collections;
  - preserve foreign HidHide blocked-device entries;
  - preserve foreign application whitelist entries;
  - acquire the Addon's exact executable whitelist lease before activation/mutation;
  - if current HidHide state cannot be safely read or mutated, fail closed;
  - rollback removes only Addon-owned changes;
  - ambiguous ownership remains recovery evidence rather than being guessed away.

Changing Gordon to Steam Deck does not change these physical-isolation rules.

===============================================================================
9. PNP OWNERSHIP OF THE VIRTUAL OUTPUT
===============================================================================

Physical-input identity and virtual-output identity are separate concerns.

The Addon continues to use before/after Windows PnP snapshots and ownership correlation to identify the virtual output it created.

For the Steam Deck path the expected target becomes:

  VID 28DE
  PID 1205

Do not replace exact Addon ownership proof with a generic "Valve controller present" test.

VIIPER `GetUSBDeviceIdentity` remains logical VIIPER identity only; it does not replace Windows PnP instance/container/ancestor evidence.

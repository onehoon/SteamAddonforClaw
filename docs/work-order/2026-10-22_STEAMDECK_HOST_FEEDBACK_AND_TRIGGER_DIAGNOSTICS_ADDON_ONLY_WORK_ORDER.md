## 1. Purpose

Collect sufficient evidence to determine whether **Death Stranding Director's Cut** (and Steam Input itself) sends haptic/rumble commands to our virtual Steam Deck when the user operates LT/RT, and determine whether those commands reach the existing physical MSI Claw PID1902 rumble sink.

The user has explicitly limited the product goal:

- Honor output feedback actually generated by the game or by configured Steam Input actions.
- Do **not** synthesize rumble from LT/RT position, pressure thresholds, virtual button transitions, game identity, or guessed behavior.
- A future, separate implementation decision may translate previously ignored **received** host feedback. This PR only captures evidence.

**No rumble feature, control behavior, protocol mapping, timing, or routing change belongs in this PR.**

## 3. Verified current code paths

### 3.1 Host-output receive path already works without a VIIPER API change

`src/SteamInputAddonforClaw/VirtualOutput/Viiper/CanonicalSteamDeckSession.cs` registers the existing native `SetSteamDeckOutputCallback` through the rooted `CanonicalViiperNativeApi` callback surface.

`src/SteamInputAddonforClaw/Feedback/PresentationRumbleFeedback.cs`:

- `SteamDeckRumbleFeedbackAdapter.TryArm` registers the callback and already logs arm success/failure at Info/Warn.
- `OnOutput(nuint handle, nint data, uint length)` copies up to 512 bytes from the native callback, decodes with `SteamDeckRumbleDecoder.Decode`, and currently **returns silently** when `!decoded.HasPhysicalTranslation`.
- Supported feedback is sent to the one existing `IPhysicalRumbleSink` under the current callback write gate. An existing timer handles the established STOP policy.
- Unlike the Xbox360 feedback bridge in the same file, the Deck branch has no per-callback receive/write correlation diagnostics.

`src/SteamInputAddonforClaw/Feedback/SteamDeckRumbleDecoder.cs`:

- `0xEB`: decoded and translated to two physical motor values.
- `0xEA`: decoded and translated using the existing Claw fallback; `CommandType == 0` is treated as STOP by the adapter.
- `0x8F`: decoded into `SteamDeckHapticPulseMetadata`, but `HasPhysicalTranslation` is false; ignored by the adapter.
- `0xDC`: currently classified as `Unknown`, with no output.
- Other configuration/unknown/malformed messages must not acquire new physical-translation behavior.

### 3.2 Existing physical output telemetry

`src/SteamInputAddonforClaw/Devices/MSI/Claw/MsiClawRumbleSink.cs` already logs successful actual changes as `Rumble TX` with `Large16`, `Small16`, `Large8`, `Small8`, and `WriteMs`. It also reports endpoint absence, failures, and STOP-retry results.

The sink may return `Succeeded/Unchanged` without a new HID write. Therefore **callback received**, **semantic output accepted**, and **physical HID write performed** are separate facts. Preserve that distinction in the diagnostic records rather than labelling every successful `SetRumble` call a hardware TX.

### 3.3 Existing correlated input source

`src/SteamInputAddonforClaw/VirtualOutput/Viiper/CanonicalSteamDeckInputPublisher.cs`:

- `PublishCurrentStateOnce` already maps the latest physical input to `SteamDeckDeviceState`, then calls `_sink.SetState(state)`.
- The target's `LTrigger` and `RTrigger` are 16-bit scaled values (0..32767), and `L2Digital` / `R2Digital` are the digital full-pull indicators.
- The publisher normally ticks at 4 ms, so never emit logs on every tick.

`src/SteamInputAddonforClaw/VirtualOutput/Viiper/SteamDeckDeviceStateMapper.cs` already performs the trigger scaling. Do not alter the mapper or physical input collection.

## 5. Steam Deck host feedback diagnostic event

### 5.1 Placement and ordering

Instrument the existing `SteamDeckRumbleFeedbackAdapter.OnOutput` path.

The important boundary is:

`Marshal.Copy -> Decode -> [diagnostics] -> HasPhysicalTranslation test -> current motor write/STOP path`

The first observable diagnostic point must execute **before the current early return** for `0x8F`, `0xDC`, unknown and malformed frames. This is the central requirement: silent drops today are the evidence gap.

Preserve exactly the current handling:

- `!HasPhysicalTranslation` still returns without motor output, without canceling/replacing the current safety timer, and without calling `_sink.SetRumble`.
- Supported `0xEB`/`0xEA` still perform exactly the existing calculation and sink write.
- `CommandType == 0` remains an explicit STOP.
- `ScheduleSafetyStop` keeps its current timing and cancellation logic.
- Callback exceptions remain contained; never throw across the native boundary.

### 5.2 Event schema

Use the existing `AppLog.Debug` and a stable event label, e.g. `SteamDeckFeedbackRx`, under category `Rumble` (or the existing category convention). Retain identical names for the whole PR.

For each emitted receive diagnostic:

| Field | Content |
| --- | --- |
| `Event` | `SteamDeckFeedbackRx` |
| `Presentation` | `SteamDeck` |
| `RxSeq` | Adapter-local monotonically increasing diagnostic callback number |
| `Opcode` | Two-digit hex from received byte 0, or `None` for invalid empty frame |
| `OriginalLength` | Original callback `length` |
| `CapturedLength` | Existing copied report length |
| `RawHex` | Hex of up to the **first 64 normalized bytes** of the existing copied report |
| `RawTruncated` | Whether the callback carried more than 64 bytes |
| `DecodeResult` | Existing `SteamDeckFeedbackCommand` enum |
| `HasPhysicalTranslation` | Existing decoder flag |
| `Disposition` | `Ignored`, `Stop`, `SinkAttempted`, as actually applicable |

The existing `AppLog` line includes a wall-clock timestamp. Do not add a separate timestamp owner or global sequence. Hex formatting, field-array allocation, and diagnostic sequence generation must be gated by `AppLog.IsEnabled(AppLogLevel.Debug)`.

For recognized commands, log the existing **decoded metadata**, without reinterpreting semantics:

- `0xEB`: `RumbleType`, `RumbleIntensity`, `RumbleLeftGain`, `RumbleRightGain`, and left/right 16-bit motor values (use the correct `TwoMotorRumble` channel naming).
- `0xEA`: `Haptic.Side`, `CommandType`, `UiIntensity`, `DbGain`, `IsModernSdlLayout`, `DurationMilliseconds` if present, and the existing `Strength8` result. Treat them as fields observed by the current decoder, **not verified intent from Death Stranding**.
- `0x8F`: `HapticPulse.Side`, `OnDurationMicroseconds`, `OffIntervalMicroseconds`, `Count`, `GainRaw`, `IsLinuxLayout`.
- `0xDC`: `RawHex` and the current `Unknown` classification **only**. Do not guess that byte 3 always means half/full click in this PR.
- Other commands: opcode, raw prefix, classification.

**Important:** Native VIIPER already normalizes optional leading report-ID bytes before the callback; use the existing copied buffer. Do not strip a second byte in Addon. Use the real callback-provided size (and capture length), not the declared protocol payload length, as the bounds reference for `RawHex`.

### 5.3 Physical write correlation

When the existing path calls `_sink.SetRumble`, log the outcome using the **same `RxSeq`**:

- event `SteamDeckFeedbackSinkResult`;
- `RxSeq`, `Opcode` / `DecodeResult`;
- effective `Large16` and `Small16` sent to the sink (including the `0xEA` STOP override);
- `Status` and `Reason` from `PhysicalRumbleWriteResult`;
- whether the requested frame is `Stopped`.

Prefer a short result log after the existing write rather than changing `MsiClawRumbleSink` or threading diagnostic IDs into the physical transport. Do not call `_sink.SetRumble` twice, do not force a physical write on `Unchanged`, and do not suppress failure logging.

To avoid duplicate high-volume receive/result records for `0xEB`, it is acceptable to emit **one combined diagnostic line** with both received-frame fields and the actual sink outcome, as long as:
1. ignored packets are logged at the pre-return boundary;
2. sink results are only logged after the attempt;
3. a user can correlate the received frame and its disposition;
4. the existing write/STOP ordering remains unchanged.

For safety STOP, a Debug-only `SteamDeckFeedbackSafetyStop` record with the originating diagnostic `RxSeq` and existing sink result is useful. Pass an optional local sequence into the existing scheduled operation rather than creating an independent timer or global origin-tracking subsystem. Never make the log a prerequisite for performing STOP.

### 5.4 Volume policy

This is a **short attended troubleshooting run**, not an always-on high-frequency trace engine.

- `Info` and `Off`: do not do hex formatting, per-frame string assembly, timestamp sampling, diagnostic input comparisons, or additional output writes.
- `Debug`: capture **all `0xEA`, `0x8F`, and `0xDC`** during the attended test, including ignored frames and STOPs, so short pulses are not erased by sampling. Emit the current per-frame raw bytes for those commands.
- `0xEB` may be frequent. Log the first nonzero frame, zero/STOP changes, and changed frames at a **coarse bounded cadence** (e.g. at most one routine nonzero sample every 100 ms). Record actual physical write outcomes without turning the existing async log into an unbounded per-frame stream. Use a small adapter-local last-observation snapshot; do not build a general tracing engine.
- For other unrecognized/configuration opcodes, capture the first few raw examples **per opcode** (e.g. first 4), so initial startup chatter cannot consume the entire unknown budget and hide a newly observed command. A fixed small diagnostic counter array is sufficient; no dictionary/interface/manager needed.
- Avoid unconditional full-64-byte logging of every unchanged report. Never create a new file sink or logging thread.
- Log volume control is **diagnostic-only**; it must not discard or delay any host feedback from the actual physical-output path.
- Keep current AppLog async bounded queue semantics and do not hold any lifecycle lock for formatting or disk I/O. No synchronous file writes from the callback.

The thresholds/sampling above concern **logging only**, not motor thresholds, haptic synthesis, game behavior, or actuation duration.

## 6. Trigger timeline diagnostic event (input observation only)

Instrument `CanonicalSteamDeckInputPublisher.PublishCurrentStateOnce` **after successful `_sink.SetState(state)`**, using the exact final `state` the virtual Deck has been given. Avoid new physical input polling.

Debug-only event `SteamDeckTriggerTransition`, category `SteamOutput`:

- `LTrigger`, `RTrigger` (0..32767);
- `L2Digital`, `R2Digital` (0/1);
- `PublishedStateCount`;
- `Reason` indicating an initial/press/release/large analog change/digital full-pull edge, as applicable.

Do **not** log all 4 ms samples. A small publisher-local last-log snapshot is enough:

- log the first successful observed state after startup while Debug is enabled (baseline);
- log zero -> nonzero and nonzero -> zero transitions for each trigger;
- log a digital full-pull edge even when the analog difference is small;
- log a meaningful movement from the **last logged** analog value, e.g. delta >= 2048 in 0..32767, to capture a slow pull in manageable steps;
- ignore idle repetitions and subthreshold changes;
- reset diagnostic-only snapshot when the publisher starts/restarts or Debug is turned off and later re-enabled so a new run has a clear baseline;
- never mutate `state`, alter `SetState` cadence, trigger behavior, publisher fault logic, or other input mappings.

This is timestamp **correlation**, not evidence of a causal relation or proof that an output originated in the game. The VIIPER callback cannot always distinguish a game's direct haptic request from a Steam Input-generated haptic. Both are legitimate already-generated host feedback and are in scope for **observation**.

## 7. Minimal illustrative code shape (not a paste-in implementation)

The existing adapter can support the diagnostic with no new owner:

~~~csharp
// Existing native callback has already copied the normalized report.
var decoded = SteamDeckRumbleDecoder.Decode(report);
var debug = AppLog.IsEnabled(AppLogLevel.Debug);
var rxSeq = debug ? Interlocked.Increment(ref _diagnosticRxSequence) : 0;

if (!decoded.HasPhysicalTranslation)
{
    if (debug && ShouldLogDiagnostic(report, decoded))
        LogSteamDeckReceived(rxSeq, report, length, decoded, "Ignored");
    return; // existing behavior, no motor output
}

var rumble = decoded.Command == SteamDeckFeedbackCommand.Haptic &&
             decoded.Haptic?.CommandType == 0
    ? TwoMotorRumble.Stopped
    : decoded.Rumble;

// Keep existing _callbackWriteGate, physical sink call and safety-stop policy.
// Emit Debug correlation around the existing actual sink result, not an extra write.
~~~

`ShouldLogDiagnostic` and `LogSteamDeckReceived` represent at most small **private diagnostic helpers** inside the existing adapter; they are not permission to create a new service/class hierarchy. No new public API or persistent setting.

## 9. User's optional post-merge attended capture (not a merge gate)

The user can enable **Settings -> Logging -> Debug**, then preserve the Runtime log for a concise comparison:

1. Steam Deck virtual presentation armed; game not running.
2. Launch Death Stranding Director's Cut; idle.
3. Slowly pull/release LT only, then RT only; repeat with a full pull and brief hold.
4. Exercise any Steam Input action with an explicitly configured haptic as a **separate control case**, if useful.
5. Restore the normal logging level afterwards.

Read the diagnostic timeline as:

`SteamDeckTriggerTransition -> SteamDeckFeedbackRx -> SteamDeckFeedbackSinkResult -> existing Rumble TX`.

Interpretation:

- `0x8F` or `0xDC` observed but ignored: evidence of a possible **future** host-command translation gap; no change in this PR.
- `0xEA` or `0xEB` observed and sink reports success/unchanged: investigate physical amplitude/timing/rendering with the existing sink logs; do not guess a missing upstream event.
- Game trigger action with **no Addon feedback receive at all**, despite a confirmed armed callback: a **separate VIIPER host-output diagnostic investigation** may be warranted (`HandleTransfer` / `HandleControl` -> `handleHostCommand` -> typed C callback). Do not presume the game must send feedback.
- Do not claim a command is game-originated solely from timing proximity to an LT/RT transition.

## 10. Explicit exclusions / anti-overengineering constraints

- add a per-game profile, user-facing haptic toggle, settings migration, UI, telemetry, external capture process or special log file;
- add a second device/logging/feedback authority, state machine, manager, wrapper, global registry or new locking tier;
- change VIIPER (Go/C ABI), USB/IP report handling, `libVIIPER.log`, controller routing, HidHide, PID1901/1902, startup ownership or suspend/restart/recovery;
- treat speculative thread interleavings as blockers or create synchronization solely for theoretical races.

Use the existing ownership and cleanup invariants. Review for realistic issues only: incorrect callback observation, accidental motor writes, missed existing STOP, hot-path logging floods, actual lifecycle regressions, and test failures.

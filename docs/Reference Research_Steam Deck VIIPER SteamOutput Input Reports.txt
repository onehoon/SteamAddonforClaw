1. ACTIVE TARGET
===============================================================================

The Addon composes one active Steam virtual output:

  Device: Steam Deck
  VID:    0x28DE
  PID:    0x1205

The Addon uses the canonical typed `lib/viiper` API, a typed Deck session, the
Deck identity resolver, the Deck mapper, and the Deck publisher. The native
library provides generic callback capability; Addon rumble/haptic adoption is
not implied by the basic input result.

===============================================================================
2. STEAM DECK STATE CONTRACT
===============================================================================

The Deck state contains native semantic fields for:

  left/right sticks, L3/R3, analog triggers, digital L2/R2,
  rear buttons, Steam, Quick Access, trackpads, and motion fields.

The initial Addon mapper sends normalized MSI Claw controller state to the
validated basic fields. Trackpads and motion remain neutral until their
separate feature tracks are implemented and validated.

===============================================================================
3. MSI CLAW MAPPING
===============================================================================

  A/B/X/Y             -> A/B/X/Y
  D-pad               -> D-pad
  LB/RB               -> LB/RB
  analog LT/RT        -> analog LT/RT
  digital LT/RT       -> digital L2/R2
  left/right sticks   -> left/right sticks
  L3/R3               -> L3/R3
  M1/M2               -> Deck rear-button fields
  Steam               -> Steam
  Quick Access        -> Quick Access

Analog trigger travel and digital full-pull state are independent inputs.

===============================================================================
4. IDENTITY AND OWNERSHIP
===============================================================================

The resolver requires exact vendor/product identity, stable instance identity,
and verified ownership evidence. Case-insensitive instance comparison is part
of the identity contract. Missing, ambiguous, or unstable candidates fail
closed.

The Addon does not infer ownership from VID/PID counts or friendly names. It
preserves unrelated devices and HidHide entries and removes only exact owned
resources during teardown.

===============================================================================
5. LIFECYCLE AND VALIDATION
===============================================================================

The routing sequence is:

  native mode -> physical input -> physical isolation -> Deck output

Publisher faults, native failures, PnP ambiguity, HidHide failures, recovery
failures, and teardown failures stop routing and preserve recovery evidence.

MSI Claw EX hardware has validated the basic non-gyro controller input path.
Lifecycle, suspend/resume, recovery, rumble, haptics, gyro, and IMU require
separate validation evidence.

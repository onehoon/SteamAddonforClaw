10. HHC — GENERAL VIIPER TARGET LIFECYCLE
===============================================================================

SOURCE FACT:

HHC VIIPERTarget.Connect():

  1. requires ViiperServerManager running
  2. obtains or creates a VIIPER bus
  3. AddDevice(busId, DeviceType, vendorId, productId)
  4. if device add fails:
       invalidate bus ID
       obtain/create another bus
       retry device add
  5. stores returned device ID
  6. subscribes to feedback/output
  7. marks target connected

Disconnect/Cleanup:

  - unregister feedback event
  - RemoveDevice(exact busId, exact deviceId)
  - clear local IDs
  - clear service reference

Dispose calls Disconnect.


PROJECT DECISION:

Use exact bus/device ownership.

Do not treat "a VIIPER device exists" as sufficient ownership evidence.

The addon must know the exact in-process:

  busId
  deviceId

for normal clean rollback.

11. VIIPER ADDDEVICE SUCCESS IS NOT WINDOWS-PNP SUCCESS
===============================================================================

CRITICAL SOURCE FACT — VIIPER C API:

viiper_device_add_ex():

  - creates the virtual USB device
  - adds it to the internal VIIPER bus
  - discovers its VIIPER device ID
  - attempts auto-attach to Windows through usbip-win2
  - if auto-attach fails, it logs the failure

The auto-attach failure is NOT necessarily returned as a fatal
viiper_device_add_ex failure.

The source explicitly allows the caller to retry attachment separately.


PROJECT DECISION:

PR #78 must NOT define creation success as:

  AddDevice(...) == 0

Creation is complete only after the exact Windows PnP output identity is
observed and verified.

Required conceptual contract:

  AddDevice success
      +
  Windows PnP appearance
      +
  exact own-virtual identity resolution
      =
  SteamOutput creation success


===============================================================================
12. VIIPER WINDOWS ATTACH PATH
===============================================================================

SOURCE FACT:

The pinned VIIPER implementation attempts local Windows USB/IP attach with:

  first:
    usbip-win2 native/IOCTL attach path

  fallback:
    usbip.exe-style path

The embedded API therefore eventually appears to Windows as a USB/IP-backed
virtual USB device.

PROJECT IMPLICATION:

A VIIPER output can look sufficiently "physical" in Windows PnP that
VID/PID-only or "USB means physical" classification is unsafe.

This reinforces the existing project rule:

  Track addon-owned VIIPER outputs explicitly by creation-time identity.

14. TRACKER API GAP — PUBLISH DOES NOT RESOLVE UNCERTAINTY
===============================================================================

SOURCE FACT:

Current tracker behavior:

  MarkOwnershipUncertain()
    -> clears known IDs
    -> sets uncertainty

  Publish(device)
    -> adds ID
    -> does NOT clear uncertainty

  ClearUncertaintyAfterVerifiedAbsence(...)
    -> only clears uncertainty if no matching candidate exists


PROJECT DECISION:

#78 likely needs a minimal atomic resolution API, conceptually:

  ResolveOwnership(verifiedDevices)

that:

  - publishes the exact verified addon-owned instance IDs
  - clears uncertainty in the same ownership transition

Do not work around this by:
  - publishing then globally clearing without checking identity
  - marking the output as external temporarily
  - excluding every 28DE:1102 device

18. CLASSIC STEAM CONTROLLER USB DESCRIPTOR
===============================================================================

SOURCE FACT — VIIPER:

Default USB device descriptor:

  USB version: 0x0200
  Device class: 0
  Max EP0 packet: 0x40
  VID: 0x28DE
  PID: 0x1102
  bcdDevice: 0x0100
  Manufacturer string: "Valve Software"
  Product string: "Wired Controller"
  One configuration

The virtual device is composite with three HID interfaces:

  interface 0:
    Keyboard
    HID boot-keyboard style
    endpoint 1 IN
    8-byte report

  interface 1:
    Mouse
    HID mouse
    endpoint 2 IN
    4-byte report

  interface 2:
    Controller
    vendor page 0xFF00
    endpoint 3 IN
    64-byte report
    64-byte input/output/feature report definitions

Controller endpoint max packet:
  0x0040

Controller interval:
  0x06


PROJECT DECISION:

Do not reconstruct this descriptor in SteamInputAddonforClaw.

Use VIIPER's `"steamcontroller"` implementation and let VIIPER own the
descriptor/feature-report protocol.

HHC scales Claw normalized 0..255 trigger axis to:

  raw = byteValue * 26000 / 255

31. CRITICAL TRIGGER ROUND-TRIP BEHAVIOR
===============================================================================

CRITICAL SOURCE FACT — VIIPER:

The C API does not blindly forward the caller's 64 bytes to the USB host.

For steamcontroller:

  incoming C# 64-byte report
    ->
  InputState.UnmarshalBinary()
    ->
  SteamController.UpdateInputState()
    ->
  VIIPER later rebuilds the host-visible Gordon report

During UnmarshalBinary():

  byte 8 L2/R2 full bits are NOT stored as independent normalized fields.

The trigger state is reconstructed from raw trigger fields.

During buildReport():

  L2/R2 digital/full bits are regenerated from the trigger raw values.

Full bit is emitted when:

  triggerRawToByte(raw) >= 0xFF

which requires raw at or above:

  26000


PROJECT DECISION:

Physical Claw full-trigger buttons:

  Buttons[6] / LeftTriggerFull
  Buttons[7] / RightTriggerFull

must not be represented only by byte 8 bits.

If a physical Full input is true, #79 should ensure the corresponding raw
trigger state reaches at least/max:

  26000

before SetInput.

Otherwise the direct byte8 full bit can disappear during VIIPER's
Unmarshal -> normalized state -> rebuild round trip.


===============================================================================
32. TARGET BUILDER TRIGGER CHANGE REQUIRED FOR #79
===============================================================================

SOURCE FACT — current target builder:

Current builder:

  - sets byte8 full-trigger bits from GamepadButtons.LeftTriggerFull /
    RightTriggerFull
  - independently converts TriggerState byte to 0..26000 raw

That is logically correct for a raw Gordon packet but not sufficient when the
packet goes through VIIPER's InputState normalization.


PROJECT DECISION:

#79 must harden trigger encoding.

Conceptually:

  leftRaw = scale(analogLeft)

  if LeftTriggerFull:
      leftRaw = 26000

  rightRaw = scale(analogRight)

  if RightTriggerFull:
      rightRaw = 26000

Then write the same raw values consistently to:
  24/26
  50/52
  and derived 11/12 representation.

Tests must validate behavior through VIIPER-compatible round-trip semantics,
not only inspect the pre-VIIPER C# buffer.

33. FRAME COUNTER OWNERSHIP
===============================================================================

SOURCE FACT — target builder:

Current C# builder accepts a uint frame and writes it at bytes 4..7.

SOURCE FACT — VIIPER:

The C API parses that field into InputState.Frame.

SteamController.UpdateInputState then updates its internal current state and
increments/assigns its own effective frame as part of device state updates.

The USB host-visible report is built from VIIPER's device state.


PROJECT DECISION:

Do not treat the C# frame argument as the authoritative USB-host sequence.

#79 should:
  - document that VIIPER owns effective host-visible frame progression
  - avoid building correctness tests around a specific client-side frame
    increment unless the current VIIPER behavior requires it

A future cleanup may remove or de-emphasize the C# frame parameter if it is
not useful outside unit tests.

35. VIIPER HOST POLLING VS CLIENT STATE UPDATES
===============================================================================

SOURCE FACT:

VIIPER stores the latest normalized state.

The host-facing controller endpoint builds reports from the current snapshot.

Therefore:
  VIIPER USB host polling
and
  addon SetInput update events
are separate layers.

PROJECT DECISION:

The addon should maintain a predictable active-state publisher rather than
assuming every physical DirectInput event maps 1:1 to one Steam USB transfer.

Initial parity choice:
  250 Hz active-only SetInput loop.

50. #78 VIRTUAL-DEVICE RECOVERY — MINIMUM SAFE CONTRACT
===============================================================================

There are two distinct recovery situations.


A. Normal in-process rollback

Known:
  exact busId
  exact deviceId
  exact Windows own-virtual identity

Can perform:
  stop publisher
  RemoveDevice(busId, deviceId)
  wait for/verify PnP absence
  clear tracker ownership
  checkpoint journal


B. Startup after process crash

Not safely known:
  old in-process VIIPER server object
  usable old bus/device handles
  whether Windows usbip-win2 already detached the PnP device

Known from journal:
  exact Windows identity that was created/owned


MINIMUM PROJECT DECISION:

Startup:

  inspect exact journaled addon-owned virtual identities

  if exact identity is absent:
      treat actual virtual mutation as already restored
      checkpoint/complete that recovery item

  if exact identity is still present:
      do NOT guess
      do NOT delete journal
      do NOT broadly detach USB/IP devices
      mark recovery unsafe / remain passive

until an exact stale-detach primitive is independently verified.


===============================================================================
51. CREATION-TO-IDENTITY CRASH WINDOW
===============================================================================

A fundamental timing window exists:

  create VIIPER device
      ->
  Windows PnP appears
      ->
  exact Windows instance identity becomes knowable

If the process crashes after creation but before exact identity journaling,
the persistent journal may not yet know which PnP instance was created.


PROJECT DECISION:

#78 must explicitly model this window.

A safe implementation should combine:

  pre-create ownership uncertainty
  +
  pre-create recovery intent / mutation boundary
  +
  immediate after-create identity resolution
  +
  exact identity replacement/checkpoint
  +
  compensation on any failure

Do not pretend this window does not exist.


IMPLEMENTATION NOTE:

The exact journal representation should be chosen in #78 after reading the
current RecoveryManager APIs.

Do not persist transient in-process bus/device IDs as if they were durable
Windows identities.


===============================================================================
52. STARTUP PRESENT-DEVICE RECOVERY IS A STOP CONDITION, NOT A GUESSING TASK
===============================================================================

If startup finds an exact journaled Gordon PnP identity still present and no
verified exact detach mechanism exists:

  stop normal routing
  preserve evidence
  report recovery unsafe

This is preferable to:

  - removing arbitrary USB/IP devices
  - resetting all VIIPER state
  - clearing all matching 28DE:1102 devices
  - deleting the journal

===============================================================================

DIRECT SOURCE FACTS:

HHC:
  - Classic Steam Controller target is 28DE:1102.
  - DeviceType is "steamcontroller".
  - Input length is 64.
  - HHC uses 250 Hz master interval for this target.
  - HHC removes/disposes virtual controller during target-mode changes.
  - HHC suspend removes virtual controller and stops VIIPER; resume restores it.
  - HHC Gordon input bit/axis layout is as documented above.
  - HHC maps generic right stick click to right-pad press.
  - HHC Claw DInput mapping confirms the physical controls listed above.

VIIPER:
  - default Gordon VID/PID is 28DE:1102.
  - "msi-claw" alias is a Steam Deck-type 28DE:12FA profile, not Gordon.
  - Gordon is a composite keyboard/mouse/controller device.
  - controller interface has 64-byte vendor HID reports.
  - VIIPER implements Gordon feature commands/settings.
  - viiper_device_add_ex auto-attaches to Windows but attach failure is not
    necessarily fatal to AddDevice.
  - SetInput parses the 64-byte report into InputState.
  - host-visible report is rebuilt from normalized state.
  - digital trigger-full bits are regenerated from raw trigger state.
  - raw max is 26000.
  - neutral quaternion W defaults to 0x4000 when all quaternion fields are zero.
  - clean viiper_shutdown removes managed buses/devices from the embedded
    server and clears internal tracking.

DS4Windows:
  - VIIPER output creation is paired with explicit own-virtual discovery.
  - before/after snapshot is used for new virtual Sony output registration.
  - output removal/disconnect uses exact output ownership.
  - newly created virtual output and HidHide interaction requires explicit
    protection in a real controller-management implementation.

SteamInputAddonforClaw:
  - current VIIPER native wrapper already exposes required core C APIs.
  - embedded binary has pinned source/build/hash provenance.
  - AddonOwnedVirtualDeviceTracker supports exact IDs and uncertain ownership.
  - ExternalControllerDetector becomes Indeterminate while own-virtual identity
    is uncertain.
  - current Gordon builder already implements most non-gyro mapping.
  - recovery schema already has AddonOwnedVirtualDevices but startup recovery
    currently rejects virtual-device mutations.


PROJECT INFERENCES / DECISIONS:

  - use explicit "steamcontroller" 28DE:1102, never "msi-claw".
  - use explicit loopback server.
  - AddDevice success is insufficient; PnP identity verification is mandatory.
  - combine before/after PnP delta with exact topology for own-output identity.
  - tracker needs an atomic resolved-ownership transition.
  - do not mutate pre-existing HidHide entries that hide a newly created output.
  - crash startup may clear virtual recovery only after exact absence is verified;
    present stale device is a fail-close condition until exact detach is proven.
  - #78 remains neutral and production-disabled.
  - #79 uses 250 Hz active publisher.
  - #79 must force raw trigger to 26000 for physical full-trigger input.
  - M2 -> Left Grip, M1 -> Right Grip.
  - right stick -> Gordon right pad.
  - Guide remains unmapped without evidence.


HARDWARE-VERIFICATION-ONLY ITEMS:

  - exact Windows PnP/container topology of created Gordon output.
  - whether usbip-win2 always detaches device after abrupt process crash.
  - whether right-pad touch threshold needs adjustment for Claw stick noise.
  - actual Steam recognition and key/axis behavior.
  - whether lizard-mode startup can cause observable phantom keyboard/mouse input.
  - exact sleep/hibernate behavior on Windows 11/MSI Claw.

82. IMPORTANT OPEN QUESTION — CRASH DETACH
===============================================================================

This research intentionally does NOT close the following question:

  Does the currently deployed usbip-win2 path guarantee that a Windows-attached
  Gordon PnP device disappears after libVIIPER host process crash without an
  orderly detach?

The reviewed HHC/DS4Windows/VIIPER sources did not provide enough evidence to
make that guarantee.

Do not turn an assumption into recovery logic.

This should be answered by:
  1. an exact upstream/driver source proof, or
  2. a controlled runtime PoC on Windows 11, preferably followed by source
     confirmation.

83. IMPORTANT OPEN QUESTION — POWER-CYCLE / PNP TIMING
===============================================================================

Windows PnP arrival/removal is asynchronous from the add/remove API perspective.

#78 must define bounded wait/verification behavior.

Do not:
  Thread.Sleep(fixed magic duration)
  -> assume success

Prefer:
  event-driven or bounded polling against exact PnP identity.

Exact timeout values can be decided from existing project patterns and hardware
measurement.

===============================================================================
86. FINAL RECOMMENDATION
===============================================================================

The current codebase is already well-positioned for #78/#79.

The most important findings that change implementation detail are:

1. Use explicit:
     "steamcontroller"
     28DE:1102
   not VIIPER alias "msi-claw".

2. AddDevice API success is not enough.
   Windows PnP output identity must be verified.

3. Own-virtual identity needs a before/after snapshot and an uncertainty gate.
   Current tracker needs a resolved-ownership transition.

4. Do not remove a pre-existing HidHide blacklist entry merely to make the new
   virtual output visible.
   Fail and compensate instead.

5. Crash persistence of usbip-win2 PnP is not proven.
   Recovery must verify absence and fail closed on unresolved presence.

6. HHC's deployed Gordon target is a strong 250 Hz precedent.

7. VIIPER parses and rebuilds Gordon input.
   Therefore the physical L2/R2 full-click must force raw trigger = 26000;
   writing only the Gordon digital bit is not sufficient.

8. VIIPER owns the effective host-visible state/frame semantics.
   Do not over-specify a client frame counter.

9. M2 -> Left Grip and M1 -> Right Grip remain authoritative.

10. #78 and #79 should use the same research basis but remain separate
    implementation PRs.
